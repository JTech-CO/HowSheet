## 런타임 이슈 - `pnpm build` 네이티브 크래시 (해결)

M1 게이트를 처음 통과시킨 뒤 재실행에서 `pnpm build`가 종료 코드 **3221226505**(`STATUS_STACK_BUFFER_OVERRUN`, 0xC0000409)로 죽었다. 원인을 다음 순서로 좁혔다.

| 실험                                           | 결과       |
| ---------------------------------------------- | ---------- |
| `dist/` 없는 상태에서 build 3회                | 3/3 성공   |
| `dist/` 있는 상태에서 build 5회                | 0/5 성공   |
| `--emptyOutDir false` + 기존 `dist/`           | 성공       |
| `--sourcemap false` + 기존 `dist/`             | 실패       |
| 빈 `outDir dist2`에 stale 파일 두고 build      | 실패       |
| `node -e "fs.rmSync('dist',{recursive:true})"` | **크래시** |
| 같은 호출을 ASCII 임시 경로에서                | 성공       |
| 수동 순회 삭제(`unlinkSync`+`rmdirSync`)       | 성공       |

**결론**: Vite 버그가 아니다. Node **25.2.0** 빌드의 `fs.rm(recursive)`가 비ASCII 경로에서 프로세스를 하드 크래시시킨다. Vite의 `emptyOutDir`가 그 호출을 쓰기 때문에 빌드가 죽었다.

fnm으로 설치된 다른 런타임을 같은 경로에서 교차 검증했다.

| Node    | `fs.rmSync(recursive)` on 비ASCII 경로 |
| ------- | -------------------------------------- |
| 24.19.0 | 정상                                   |
| 24.20.0 | 정상                                   |
| 25.2.0  | **프로세스 크래시**                    |
| 25.9.0  | 정상                                   |

**조치**: `.nvmrc`를 24.20.0 LTS로 고정하고 `engines`에 `>=24.20.0 <25.0.0`을 지정했다. `emptyOutDir`는 표준값(정리 수행)으로 되돌렸고 임시 워크어라운드는 제거했다. pnpm의 `engine-strict`가 루트 프로젝트의 `engines`를 강제하지 않는 것을 실측 확인해(25.2.0에서 설치 성공), `scripts/check-node.mjs`를 `preinstall`·`dev`·`build`에 물려 실제로 차단하게 했다.

## 남은 경고

- ESLint 9.39.5는 npm에서 deprecated로 표시된다(10이 최신). `eslint-plugin-jsx-a11y` 6.10.2가 ESLint 10을 지원하지 않아 의도적으로 고정했다.
- TypeScript 5.9.3도 최신(7.0.2)이 아니다. `typescript-eslint` 8.68.0의 peer 범위가 `<6.1.0`이다.
- 두 항목 모두 상류 플러그인이 지원을 추가하면 함께 올린다. `PROGRESS.md` 결정 로그 참조.
- `pnpm install` 시 pnpm이 11.24.0 업데이트 안내를 출력한다. `packageManager` 고정 값이므로 무시한다.
- `pnpm exec playwright install chromium --with-deps`는 Windows에서 무출력 종료했다. `--with-deps` 없이 재실행해 정상 설치됐다. Linux CI에서는 `--with-deps`가 필요하다.
- `deploy.yml`은 `workflow_dispatch`만 열려 있다. 실제 호스트 배포와 SPA 폴백 검증은 M12에서 한다.

## 이후 정정 (2026-09-02, M6 진입 전 감사)

M1~M5의 DoD를 저장소 실제 상태와 다시 대조하면서 이 보고서의 세 가지가 사실과
어긋나는 것을 확인했다. 판정 자체는 지금도 충족이지만 근거가 실제보다 강하게
적혀 있었다.

- **DoD 2의 근거.** "`.npmrc`의 `save-exact=true`가 강제"라고 적었으나, M1 시점에
  이 DoD를 판정하는 검사는 없었다. 실제로 M4와 M5에서 추가한 8종이 전부 캐럿
  범위로 들어왔고 두 phase가 그대로 통과했다. 게이트(`verify:dependencies`)는
  M5에 와서야 생겼다. 설정은 의도이고 검사는 사실이다.
- **테스트 수치가 PROGRESS.md와 어긋난다.** 이 보고서는 "83 passed", 당시
  `PROGRESS.md` 검증 로그는 "46 passed"였다. 적대적 검토 후 재실행한 수치가
  한쪽에만 반영됐다.
- **"규칙 7종"에 코드 근거가 없다.** M1 커밋의 스크립트는 요약 문자열에 7을
  하드코딩했을 뿐이고 실제 규칙 종류는 6개다. 현재 코드는 `RULE_KINDS.length`를
  출력한다.

domain에도 걸고 음성 검증했다(`src/domain/__probe.tsx` → `DOMAIN_PURITY` 1건).
