## 적대적 검토 후 수정

4개 관점 검토에서 blocker 5건과 다수의 major가 나왔고, 그 과정에서 검토가 닿지 않은 결함도 하나 드러났다. 전부 수정했다.

### 검토가 지적한 것

1. **메모리 백엔드가 살아 있는 참조를 저장·반환했다.** `guides.get(id) === savedObject`가 참이라 트랜잭션 안의 제자리 수정이 스냅샷 롤백을 그대로 통과했다. DoD 3과 INV-08이 IndexedDB에서만 성립하고 **정작 폴백 모드에서 깨져 있었다.** 저장 경계에서 값을 복사하도록 고쳤다(`cloneStored`).
2. **`withSnapshot`이 새 가이드를 보호하지 못했다.** `capture()`가 아직 없는 가이드에 `undefined`를 돌려줘 실패 시 되돌리기가 무동작이었다. 스냅샷에 `existed` 상태를 넣고, 없던 가이드는 "지우기"로 되돌린다.
3. **`withSnapshot`이 문서만 되돌리고 자산을 되돌리지 않았다.** 실패한 가져오기가 이미지 바이트를 영구히 지울 수 있었다. 작업 전체를 트랜잭션으로 감싸 자산까지 함께 롤백한다.
4. **트랜잭션 조기 커밋.** 콜백이 저장소 밖 Promise를 그냥 await하면 실제 브라우저에서 IndexedDB 트랜잭션이 그 사이에 커밋된다. 정식 대기 경로 `tx.waitFor()`를 노출하고, 트랜잭션 스코프 이탈을 `TransactionEscapedError`로 즉시 실패시킨다. 그래도 남는 부분 커밋은 `withSnapshot`의 두 번째 겹이 치운다.
5. **`restore()`에 되돌리기 취소가 없고 성공 시 스냅샷이 남았다.** 오래된 스냅샷이 나중에 새 작업을 조용히 덮어썼다(revision 9 → 1). 성공한 작업은 같은 커밋에서 스냅샷을 지우고, `restore()`는 1회성이며 직전 문서를 `replaced`로 돌려준다.
6. **중첩 트랜잭션 의미가 두 백엔드에서 달랐다.** 메모리 백엔드는 안쪽 실패를 바깥이 삼키면 그대로 커밋했다. Dexie처럼 부모를 오염시켜 커밋을 막는다.
7. **`close()` 의미가 달랐다.** 메모리 백엔드가 내용을 지워, 방어적으로 close를 부르는 호출자가 데이터를 잃었다. Dexie와 같이 연결만 닫고 이후 사용은 `StorageClosedError`로 막는다.
8. **`openStorage`가 무한정 기다릴 수 있었다.** `open()`에 시간 제한을 두고, 실패 시 열다 만 연결을 닫는다.
9. **`PreferenceStore.set`이 밖으로 던질 수 있었다.** 저장소의 `length` getter가 던지면 세션 전환 자체가 실패했다. 이 메서드가 던지는 경우는 허용 목록 위반뿐이라는 계약을 지키도록 고쳤다.
10. **`verify:architecture`의 저장소 규칙이 패키지만 봤다.** `window.localStorage` 직접 사용이 모든 게이트를 통과했다. 전역 검사를 추가했다(위 음성 검증).
11. **경합으로 생길 수 있는 고아를 치울 경로가 없었다.** `findOrphanAssets`는 "찾기"만 했다. `removeOrphans()`를 추가하고 고아 탐지를 트랜잭션 안에서 읽도록 바꿨다. `AssetRepository.put`의 중복 확인과 쓰기도 한 트랜잭션으로 묶었다.

### 검토가 닿지 못한 것 — 통합 테스트가 IndexedDB를 쓰고 있지 않았다

두 백엔드 동등성 테스트를 붙이고 나서 드러났다. `fake-indexeddb/auto`는 import 시점에 전역 `indexedDB`를 채우는데, ESM은 import를 선언 순서대로 평가하므로 테스트 파일이 `@/storage/db.ts`를 먼저 import하면 **Dexie가 전역이 빈 상태로 먼저 평가된다.** 그러면 `openStorage`가 `MissingAPIError`를 만나 설계대로 **조용히 메모리 백엔드로 떨어진다.**

즉 46개 중 34개가 IndexedDB를 한 번도 건드리지 않은 채 통과하고 있었다. M3의 "IndexedDB 통합 테스트"라는 주장 자체가 사실이 아니었다. 두 가지로 막았다.

- `tests/setup/fake-indexeddb.ts`를 `dom` 프로젝트의 `setupFiles`로 등록해 import 순서에 의존하지 않게 했다.
- 테스트 도우미가 백엔드를 명시하지 않은 경우 `mode !== 'indexeddb'`이면 이유를 담아 **실패시킨다.** 제품 코드의 조용한 폴백은 옳지만, 테스트에서는 게이트가 사라지는 것과 같다.

이 수정 직후 곧바로 다음 결함이 드러났다. **jsdom의 `Blob`은 fake-indexeddb의 구조화 복제를 지나면 빈 객체가 된다.** 이미지 바이트가 통째로 사라지는데 `blob` 필드는 존재하므로 아무 단언도 걸리지 않는다. 자산 본문 표현을 `ArrayBuffer`로 바꿨다(아래 결정 참조).

## 성능·접근성·보안 수치

- 편집기 번들: JS 231.46 kB (gzip 74.33 kB) — 저장소 모듈은 아직 앱에서 import되지 않아 M2 대비 변화 없음. 실제 증가는 M4에서 측정한다.
- 보안: LocalStorage 키는 허용 목록 밖이면 쓰기 거부. 비밀번호·복구 코드·원문 파일 경로 키는 명시적 거부 테스트로 고정(기술 §7.2).
- 커버리지: M3 게이트가 요구하지 않아 측정하지 않았다. 목표치 판정은 M12.

## 남은 경고

- **조기 커밋 실패 모드 자체는 통합 테스트로 재현되지 않는다.** fake-indexeddb가 유휴 시 자동 커밋을 실제 브라우저만큼 엄격히 흉내 내지 않는다(0·5·50·200 ms 지연 모두 트랜잭션이 살아 있고 롤백이 성립). 재현 가능한 두 가지 — 스코프 이탈 확인과 `tx.waitFor()` 경로 — 만 테스트로 고정했다. 실제 브라우저 경로는 M8 가져오기 E2E에서 확인한다.
- **`RecoverySnapshot.document`가 optional이 됐다.** `existed: false`를 표현하기 위해서다. 저장소 내부 타입이라 `GuideDocument` 스키마(INV-03)와는 무관하다.
- **`withSnapshot`의 되돌리기는 대상 가이드만 복구한다.** 콜백이 다른 가이드까지 건드리면 트랜잭션 롤백에만 의존한다. 현재 호출자가 없고 M8에서 계약으로 고정한다.
