## 평가셋의 모양

### 네 가지를 한 명령에서 본다

1. **생성** - 자료 5종 × 요소 조합 13종(없음·자료에 맞는 것·전부·하나씩 10) × 디자인
   135종 + 잘림 사례 5 = **8,780건**. 조립기가 만든 프롬프트가 전부 통과해야 한다.
2. **재작성** - `prompts/handwritten/` 5건과 `prompts/captured/`(지금 0건)가 통과해야 한다.
3. **카나리아** - 좋은 프롬프트 15개에 81종의 변이를 가해 기대한 검사가 **실제로
   걸리는지** 본다. 하나라도 빠져나가면 평가 전체가 실패한다.
4. **공허 방지** - 자료 종류, 요소 10종, 디자인 값 15종, 검사 8종, 금지 범주 7종마다
   빠진 것이 없는지, 검사가 본 절과 사실 후보가 0이 아닌지 센다.

## 적대 검증

이 phase의 값어치는 "나쁜 프롬프트를 잡아낸다"다(하네스 P8 주의). 스스로 쓴 카나리아만으로는
**내가 떠올린 나쁜 프롬프트**만 잡는다. 그래서 에이전트에게 채점기를 공격하게 했다.

### 1차 - 적팀 5명

첫 채점기를 에이전트 다섯이 범주를 나눠 공격했다. 후보 263건 중 **210건이 빠져나갔다.**
원인은 어휘가 모자란 것보다 구조에 있었다.

| 원인                                              | 예                                                                         |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| 절 어디에든 부정어가 있으면 절 전체를 부정으로 봄 | "과하지 않게 은은한 네온 글로우를 넣는다", "429 안내를 제외한 제목에 네온" |
| "금지"가 들어간 제목이면 구역 전체를 부정으로 봄  | "## 금지 목록 외에 허용되는 효과"                                          |
| 고르지 않은 요소를 요구 문구 그대로만 찾음        | 한 줄바꿈, 존댓말 한 번에 통과                                             |
| 결과물 요구를 낱말이 있는지로만 봄                | "인쇄는 고려하지 않아도 됩니다", "1320px"                                  |
| 규칙 문구의 작은 숫자가 무엇이든 허락함           | "## 3."의 3이 "노드 3대"를 통과시킴                                        |
| CSS 선언 예외가 HTTP 헤더를 삼킴                  | `X-RateLimit-Limit: 1000`                                                  |
| 금지 목록이 **있기만** 하면 됨                    | 취소선, HTML 주석, "무시해도 됩니다", 항목 뒤 "다만 제목은 예외"           |
| 인용이 **있기만** 하면 됨                         | 울타리 안에 "편집 메모: 위 값은 오기" 덧붙이기, 숫자만 바꾼 사본           |

고친 뒤 같은 210건을 다시 채점해 **194건이 떨어진다.** 실제로 쓸 법한 꼴 31종은
카나리아로 옮겨 `pnpm eval:prompts`가 매번 확인한다.

### 2차 - 청팀 3명

조인 채점기가 좋은 프롬프트를 떨어뜨리는지 보려고 청팀에게 좋은 프롬프트를 쓰게 했다.
세 에이전트 모두 사용량 한도로 결과를 돌려주기 전에 끊겼고, 그때까지 남긴 좋은 프롬프트
35건을 직접 채점하고 떨어진 것을 한 건씩 읽어 오탐인지 판정했다. **33건이 떨어졌다.**
적팀만 돌렸다면 모르고 지나갔을 일이다.

| 원인                               | 예                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| 절 끝만 보니 낱말 곁의 부정을 놓침 | "웹폰트를 불러오지 않도록", "그라데이션이 생기지 않도록", 표 칸 "네온 없음 \|"     |
| 평범한 CSS를 사실로 봄             | `:focus-visible`, `#111111`, `16px/1.6`, 명암비 4.5:1, A4 여백 15mm                |
| 제목으로 세운 요소를 못 봄         | "### 다이어그램" 아래 목록                                                         |
| "결과물" 제목을 요구 구역으로 봄   | "## 결과물 구성" 아래의 요소 지시가 통째로 빠짐                                    |
| 넓은 패턴                          | "점검 모드 **해제**", `#d3d3d3`의 "d3", "학습률을 크게 **올리면** 손실이 **커지**" |

고친 뒤 **35건 중 1건**만 떨어진다. 그 1건("완료 n / 12")은 자료에 없는 합계라 옳게
떨어진 것으로 본다. 오탐이던 꼴 17종을 단위 테스트로 남겼다.

같은 고침 뒤 적팀의 210건은 여전히 **194건이 떨어진다.** 청팀을 위해 푼 것이 적팀에게
길을 다시 열지 않았는지 두 방향을 번갈아 확인했다. 한 번은 열렸다 - "X 대신"의 부정
범위를 넓혔더니 "굵기 대신 명조로, 기울임 대신 필기체로"가 다시 통과해 좁혔다.

2차 적팀(두 명)은 사용량 한도로 돌지 못했다. 아래 "남은 경고" 2.

## 설계 판단

### 채점기를 `src/features/`에 둔다

앱 번들에는 들어가지 않는다(초기 gzip 137.01 → 137.05 kB, 늘어난 0.04 kB는 금지 항목
문구 변경분이다). 그래도 `src/`에 두는 이유는 도메인 규칙(`PROHIBITIONS`, `ELEMENTS`)과
조립기를 import하고, 타입 검사·린트·`verify:architecture`의 도메인 규칙을 그대로 받기
위해서다. 나중에 결과 화면에서 "금지 목록 누락"을 알리는 데 같은 모듈을 쓸 수 있다.

### 실행기는 Node가 `.ts`를 직접 돈다

`scripts/eval-prompts.ts`는 빌드 없이 `node`로 돈다. Node 24.20의 타입 제거가 `.ts`
확장자 import를 그대로 받고, 저장소가 이미 `allowImportingTsExtensions`로 쓰고 있다.
새 도구(tsx 등)를 들이지 않았다.

### 조합을 고르지 않고 전부 돈다

디자인 135종을 몇 개만 고르면 "왜 그 조합인가"가 남고, 고르지 않은 조합에서 규칙 문구끼리
부딪히는 일을 놓친다. 폰트 모순은 '혼합' × '기술' 조합에서만 나왔다. 조립기가 빨라 전부 돌아도
12초다.

### 카나리아는 파일이 아니라 변이다

나쁜 프롬프트 파일을 두면 조립기 문구가 바뀔 때마다 파일을 손으로 고쳐야 하고, 고치지 않으면
엉뚱한 이유로 떨어진다. 좋은 프롬프트에 **한 가지만** 망가뜨리면 "이 검사가 이 결함을 잡는다"가
정확히 드러난다. 바탕이 먼저 통과하는지 확인하고 변이를 가한다.

### 부정은 서술어가 정한다

한국어의 부정은 끝에 온다. 절 끝의 부정 서술어, 낱말 바로 뒤의 부정("~지 않도록", "없는"),
영어의 앞선 부정, "X 대신·X가 아니라"의 바로 앞 낱말만 부정으로 본다. 절은 연결 어미("넣고",
"쓰되", "말고", "않고", "없이")에서 끊고 쉼표에서는 끊지 않는다. 적팀·청팀이 이 선을 양쪽에서
밀어 정했다.

### 숫자는 단위와 함께 맞춘다

규칙 문구의 숫자는 단위까지 같아야 근거가 된다. 자료의 숫자는 단위 없이 적힌 표 칸이 많아
너그럽게 맞춘다. 시각 "14:00"은 "오후 2시"로 풀어 쓰는 것을 허락한다.

### 실제 AI 출력은 넣을 자리만 둔다

키를 스크립트에서 읽지 않았다. 앱의 키 경계(INV-01, P4 DoD 5)를 건드려야 하기 때문이다.
대신 사용자가 앱에서 받은 `.md`를 `prompts/captured/<사례 id>.md`로 넣으면 평가셋이 채점하고
카나리아 바탕으로도 쓴다. 절차는 AI 채점 가이드 §7.

## 이번 phase에서 드러난 것

1. **생성 프롬프트가 스스로 모순이었다.** '혼합' 타이포를 고르면 "폰트 계열은 이 셋을 넘지
   않는다"와 금지 목록의 "폰트 계열을 셋 이상 섞지 않는다"가 같은 프롬프트에 들어갔다. 기본 톤인
   '기술'이 코드를 고정폭으로 요구해 혼합을 고르면 늘 이렇게 됐다. 사용자 확정에 따라 코드용
   고정폭은 세지 않도록 두 문구와 제품정의 §5.1을 고쳤다.
2. **첫 채점기는 적팀에게 210건을 내줬고, 조인 채점기는 청팀의 좋은 프롬프트 33건을 떨어뜨렸다.**
   한쪽 방향으로만 검증했다면 어느 쪽이든 멀쩡한 게이트로 보였을 것이다.
3. **카나리아를 단위 테스트에만 두면 평가 명령은 채점기가 눈을 감아도 통과한다.** 그래서
   실행기가 매번 카나리아를 돌리고, 검사 8종·금지 범주 7종마다 잡힌 카나리아가 있는지 센다.
4. **Git Bash의 heredoc이 백슬래시를 먹는 문제가 또 나왔다.** 정규식을 고치는 스크립트가 `\s`를
   `s`로 바꿔 대상을 찾지 못했다. 편집 도구로 바꿨다.

## 남은 경고

1. **한국어로만 쓴 꾸민 사실은 잡지 못한다.** 적팀 210건 중 남은 16건 대부분이다: "플랫폼팀
   김민수 매니저", "아담 옵티마이저", "삼천 건", "다음 주 화요일", 자료 날짜를 다른 일에 붙이기,
   따옴표 없는 소문자 명령. AI 채점 가이드 §2·§3의 `grounded-korean`이 맡을 자리다.
2. **2차 적팀이 돌지 못했다.** 사용량 한도로 두 번 끊겼다. 청팀을 위해 푼 규칙이 새 우회를 열었는지는
   1차 적팀 210건을 다시 채점하는 것으로만 확인했다. 새 공격은 받지 않았다.
3. **`captured/`가 비어 있다.** 실제 Haiku 출력은 한 건도 채점하지 않았다. 재작성 5건은 사람이
   아니라 에이전트가 AI 출력처럼 쓴 예시다. 첫 실제 출력은 사용자가 앱에서 넣어야 한다.
4. **`pnpm test:unit`이 첫 실행에서 한 번 실패했다.** `anthropic.client.test.ts`의 첫 테스트가 P7에서
   동적 import로 바꾼 SDK를 차가운 캐시에서 불러오느라 5초를 넘겼다. 이어진 두 번은 667/667이다.
   P8 코드와 무관하고, 재시도나 제한 시간 늘리기로 덮지 않았다. 별도 작업으로 제안했다.
5. **규칙 문구 안의 숫자는 채점 대상이 아니다.** 조립기 골격에 꾸민 수치를 넣으면 그 수치가 규칙
   문구가 되어 근거로 잡힌다. 규칙 문구는 P3 단위 테스트가 지킨다.
6. **CI가 이 평가를 돌리지 않는다.** `.github/workflows/ci.yml`이 v1의 없는 스크립트를 부르고 있어
   통째로 손봐야 한다. 별도 작업으로 제안했다.
