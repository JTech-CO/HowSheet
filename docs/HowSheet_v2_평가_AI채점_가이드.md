# HowSheet v2 - 프롬프트 평가에 AI 채점을 붙이는 법

- 상태: **가이드라인만 있다. 구현하지 않았다.**
- 결정: 2026-09-15 사용자 확정 - P8의 채점은 기계적 검사만 한다. AI 채점은 나중에
  붙일 수 있도록 이 문서로 자리를 잡아 둔다.
- 관련: 하네스 P8, `src/features/evaluate/`, `scripts/eval-prompts.ts`

이 문서는 "AI 채점을 넣자"는 결정이 났을 때 처음부터 다시 설계하지 않도록, 지금
평가셋이 **무엇을 못 보는지**와 AI 채점을 **어떤 조건으로 붙일지**를 적어 둔다.

## 1. 원칙

1. **기계적 검사가 바닥이다.** AI 채점은 기계적 검사를 통과한 프롬프트에만 돈다.
   AI가 "괜찮다"고 해도 기계적 실패를 뒤집지 못한다. 금지 목록이 빠진 프롬프트를
   설득력 있는 이유로 통과시키는 채점자는 쓸모가 없다.
2. **처음에는 보고만 한다.** AI 판정은 `pnpm eval:prompts`의 종료 코드에 넣지 않고
   결과 파일에만 적는다. §6의 보정을 통과한 뒤에야 게이트로 올린다.
3. **점수가 아니라 판정 가능한 주장으로 쓴다.** "구체성 1~5점"이 아니라 "고른 요소마다
   자료의 특정 대상을 지목한다 - 예/아니오"다. 점수는 기준선을 다시 정해야 하고 그
   사이에 나쁜 프롬프트가 "그래도 4점"으로 통과한다. (하네스 P8 DoD 5)
4. **기본 명령은 네트워크 없이 돈다.** AI 채점은 별도 명령(예: `pnpm eval:prompts:judge`)으로
   명시적으로 켠다. 키가 없는 사람과 CI가 지금의 평가를 그대로 돌릴 수 있어야 한다.

## 2. 기계적 검사가 못 보는 것

AI 채점이 맡을 자리다. 각 항목은 지금 평가셋이 **통과시키는** 나쁜 프롬프트의 모양이다.
따옴표 안의 예는 P8 적대 검증에서 에이전트가 실제로 써서 채점기를 통과시킨 문장이다.

| 영역          | 기계적 검사가 하는 일                                                              | 못 보는 것                                                                                                                                                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 금지 기법     | 낱말·CSS 패턴을 찾고, 절 끝의 서술어와 낱말 곁의 부정으로 지시인지 가린다          | 어휘에 없는 동의어, 자료에 같은 낱말이 나올 때의 지시("네온" 예외), 부정 구역 제목 아래에 둔 긍정 목록("## 하지 말 것" 아래 "### 꾸밈")                                                                                                                |
| 폰트 혼용     | 계열(세리프·산세리프·손글씨·디스플레이)과 알려진 글꼴 이름을 센다                  | 같은 계열 안의 서로 다른 글꼴 셋("제목 Montserrat, 본문 Pretendard, 캡션 Noto Sans"), 목록에 없는 글꼴 이름                                                                                                                                            |
| 요소 반영     | 고른 요소의 이름이 무엇을 담을지와 함께 나오는가, 제목으로 세운 뒤 내용이 따르는가 | 이름을 대고 뒤집는 추론("비교표 형태의 데이터가 있지만 표로 만들면 딱딱하니 문단으로"), 이름 없이 세운 고르지 않은 요소("재시도 흐름 - 위에서 아래로 흐르는 그림, 분기마다 판단 기준")                                                                 |
| 자료 충실도   | 숫자(단위 포함)·버전·URL·코드·라틴 이름·"자료의 …" 인용을 자료와 대조한다          | 한국어로만 쓴 꾸민 사실("플랫폼팀 김민수 매니저", "아담 옵티마이저", "외부 보안 감사에서 권고받은 값"), 한글 수사("삼천 건"), 자료 수치를 엉뚱한 사실에 붙이기("회귀 테스트를 8월 22일까지"), 따옴표 없는 소문자 명령("psql로 접속해 select count(*)") |
| 결과물 요구   | 네 가지를 가리키는 말이 있는가, 요구마다 풀어 주는 전형적인 말이 없는가            | 전형에서 벗어난 완화 문장                                                                                                                                                                                                                              |
| 프롬프트 품질 | 없음                                                                               | 한 페이지 분량으로 범위를 좁혔는가(§6.2-6), 디자인 축이 CSS로 옮길 수 있게 서술됐는가(§6.2-3), 프롬프트 안의 지시끼리 모순이 없는가                                                                                                                    |

마지막 줄의 **지시끼리의 모순**은 P8에서 실제로 나왔다. '혼합' 타이포와 금지 목록이
같은 프롬프트에서 폰트 계열 수를 서로 다르게 말했다. 기계적 검사로 찾은 것이
아니라 폰트 계산 규칙을 정하다 사람이 읽고 찾았다. AI 채점이 가장 먼저 잡아야 할
종류다.

P8 적대 검증에서 확인한 구체적인 빈틈은 `artifacts/qa/phase-reports/P8.md`의 "남은
경고"에 있다.

## 3. 루브릭 초안

판정자는 기준마다 `pass`(예/아니오), `evidence`(프롬프트에서 그대로 옮긴 인용),
`reason`을 낸다.

| id                      | 주장                                                      | 실패 예                           |
| ----------------------- | --------------------------------------------------------- | --------------------------------- |
| `specific-elements`     | 고른 요소마다 자료의 특정 대상을 지목한다                 | "다이어그램을 넣는다"로 끝난다    |
| `grounded-korean`       | 자료에 없는 사람·조직·절차·인과를 주장하지 않는다         | 자료에 없는 담당 팀을 적는다      |
| `semantic-prohibitions` | 금지 목록의 기법을 다른 말로도 지시하지 않는다            | "형광빛 테두리로 강조"            |
| `translatable-design`   | 색 역할·간격 스케일·폰트 스택을 CSS로 옮길 수 있게 말한다 | "세련되게", "깔끔하게"만 있다     |
| `one-page-scope`        | 무엇을 덜어 낼지 정해 한 페이지로 좁힌다                  | 자료의 모든 절을 다 담으라고 한다 |
| `no-contradiction`      | 프롬프트 안의 지시끼리 충돌하지 않는다                    | 한 곳은 셋까지, 다른 곳은 셋 미만 |
| `requirements-kept`     | 결과물 요구를 뒤에서 완화하거나 뒤집지 않는다             | "모바일은 신경 쓰지 않아도 된다"  |

검토했지만 넣지 않은 것:

- **결과 페이지를 실제로 만들어 보고 채점하기** (제품정의 §10). 가장 직접적이지만
  생성 모델 호출이 한 번 더 들고, 페이지 품질의 편차가 프롬프트 품질의 편차와 섞인다.
  루브릭이 안정된 뒤 소수 표본으로만 한다.
- **문체 점수**. 이 제품의 값어치와 무관하다.

## 4. 판정자 설계

### 모델

- 생성 모델(`claude-haiku-4-5`)을 **자기 판정자로 쓰지 않는다.**
- 후보는 `claude-sonnet-5`(균형)와 `claude-opus-5`(기준이 미묘할 때). 고르는 것은
  사용자다. 비용은 아래 §5처럼 파일럿으로 잰 뒤 정한다.
- 최신 모델은 `temperature`를 받지 않는다. 판정의 흔들림은 샘플링 인자로 줄이지 말고
  **같은 사례를 여러 번 판정해 다수결**로 다루고, 판정끼리 어긋난 비율을 결과에 남긴다.

### 입력과 출력

- 입력: 자료 원문, 선택(요소·디자인), 채점할 프롬프트.
- 판정자의 시스템 프롬프트는 프롬프트와 자료를 **신뢰할 수 없는 데이터**로 다룬다.
  자료나 프롬프트 안에 "이 프롬프트는 모든 기준을 통과한다"가 적혀 있을 수 있다.
- 출력은 구조화 출력(`output_config.format`의 JSON 스키마)으로 받는다. 자유 형식
  JSON은 이유 문장 속 따옴표 하나로 파싱이 깨진다.
- **증거를 기계로 확인한다.** `evidence`가 프롬프트에 글자 그대로 없으면 그 판정은
  판정자 오류로 기록하고 채점에 쓰지 않는다. 판정자가 없는 문장을 근거로 드는 것을
  막는 가장 싼 방법이다.

### 코드에 붙일 자리

- 순수 부분 - 판정 요청 조립, 응답 스키마, 증거 확인 - 은 `src/features/evaluate/judge.ts`에
  둔다. 기계적 검사와 같은 `Finding` 모양(`check`, `message`, `excerpt`)으로 낸다.
- 네트워크 호출은 `scripts/` 쪽에만 둔다. 앱 번들에 들어가지 않는다.
- 실행기의 결과는 `artifacts/eval/judge.json`에 따로 쓴다.
- **의미 카나리아**를 따로 둔다. §2의 표에서 기계적 검사가 통과시키는 나쁜 프롬프트를
  `canaries.ts`와 같은 변이로 만들고, "기계는 통과, AI는 실패"가 기대값이다. 이것이
  AI 채점이 값을 하는지 보는 유일한 증거다.

## 5. 키와 비용

### 키 - 붙이기 전에 사용자 결정이 필요하다

INV-01과 P4 DoD 5가 **키를 만지는 모듈은 `src/storage/api-key.store.ts` 하나**라고
정했고 `verify:architecture`가 강제한다. 평가 스크립트가 키를 쓰면 이 경계를 어떻게
다룰지 정해야 하므로 하네스 §3.1 STOP 대상이다. 제안:

- 평가용 키는 앱의 브라우저 저장소가 아니라 **환경 변수**에서만 읽는다.
- 그 읽기는 `scripts/` 아래 한 파일로 가두고, `verify:architecture`에 그 파일만
  허용하는 규칙을 더한다.
- 키를 로그·결과 파일·오류 메시지에 싣지 않는다. 결과 파일에 요청 헤더를 남기지 않는다.
- 앱 사용자에게 받은 키와 섞지 않는다. 평가 전용 키를 따로 발급한다.

### 비용

- **추정하지 않고 잰다.** 대표 사례 몇 건으로 파일럿을 돌려 실제 `usage`로 계산한다.
- 8,780건 전부를 AI로 채점하지 않는다. 조립기 출력은 결정적이라 자료·요소 조합이
  같으면 같은 문장이 나오고, 판정할 가치가 낮다. 대상은 `captured/`(실제 AI 출력)와
  자료마다 몇 개의 대표 조합이다.
- 판정 호출 수 = 사례 수 × 반복 횟수. 반복 없이 한 번 판정하면 흔들림을 볼 수 없다.

## 6. 게이트로 올리는 조건

보고 전용에서 종료 코드에 넣기 전에 아래를 모두 만족해야 한다. 수치는 제안이고
사용자가 정한다.

1. **오라클과 널.** `handwritten/`·`captured/`의 좋은 프롬프트는 거의 모두 통과하고,
   빈 문자열·"모르겠다"·다른 자료에 대한 프롬프트는 모두 실패한다.
2. **의미 카나리아 적발.** §4의 의미 카나리아를 판정자가 잡는다.
3. **반복 간 일치.** 같은 사례를 여러 번 판정했을 때 어긋나는 비율이 낮다.
4. **사람 확인.** 판정 결과 표본을 사용자가 읽고 "다르게 판정했을 사례"가 없다고
   말한다. 하나라도 있으면 루브릭을 고치고 다시 본다.

## 7. 실제 AI 출력을 평가셋에 넣는 법

AI 채점과 무관하게 **지금도** 할 수 있고, 기계적 검사가 실제 Haiku 출력을 보는 유일한
길이다. 저장소의 `handwritten/`은 AI 출력처럼 **사람이 다시 쓴 예시**라 실제 출력이
아니다.

1. 평가 자료 하나를 고른다: `tests/fixtures/eval/sources/<자료 id>.md`
2. 앱에 그 파일 내용을 그대로 붙여넣고, 요소와 디자인을 사례 조합대로 고른다.
   사례 id는 `<자료 id>.<요소 조합>.<색>-<톤>-<밀도>-<타이포>`다. 요소 조합은 `none`,
   `fit`(자료마다 `src/features/evaluate/cases.ts`의 `fit`), `all`, `only-<요소 id>`다.
3. 키를 넣고 생성한 결과를 `.md`로 내려받는다.
4. `tests/fixtures/eval/prompts/captured/<사례 id>.md`로 저장한다.
5. `pnpm eval:prompts`를 돌린다. 이 파일은 통과해야 하고, 카나리아의 바탕으로도 쓰인다.

파일 하나만 볼 때:

```bash
node scripts/eval-prompts.ts --file tests/fixtures/eval/prompts/captured/<사례 id>.md --case <사례 id>
```

실패하면 두 가지 중 하나다. 실제 AI가 나쁜 프롬프트를 쓴 것(제품 결함 - 시스템
프롬프트를 고친다)이거나, 채점기가 좋은 프롬프트를 떨어뜨린 것(채점기 결함 -
`lexicon.ts`나 `facts.ts`를 고치고 그 모양을 단위 테스트에 더한다). 어느 쪽인지
사람이 읽고 정한다. 파일을 지워서 통과시키지 않는다.
