# HowSheet 디자인 백서 (Design Whitepaper)

**버전**: 1.0  
**작성일**: 2026년 8월 29일  
**작성자**: JTech-CO / HowSheet 프로젝트  
**참고 문서**: HowSheet 초안, HowSheet 기술 백서 v1.0, 웹 프로젝트용 디자인 백서 템플릿

---

## 1. 프로젝트 개요 (Project Overview)

### 1.1. 프로젝트 명

**HowSheet UI/UX Design - 누구나 만드는 단일 페이지 단계별 해결 가이드**

### 1.2. 목적 (Purpose)

HowSheet의 디자인은 긴 기술 문서를 보기 좋게 꾸미는 것이 아니라, 독자가 실수하지 않고 작업을 끝낼 수 있도록 **행동의 순서, 위험, 성공 조건, 다음 선택**을 명확하게 보이게 하는 데 목적이 있다.

작성자에게는 구조화된 편집 경험을 제공하고, 독자에게는 복잡한 편집 구조를 감춘 채 지금 수행해야 할 행동만 보여준다. 결과물은 모바일에서 한 손으로 진행할 수 있고, 데스크톱에서는 코드와 이미지, 오류 해결을 충분한 폭으로 확인할 수 있어야 한다.

#### 1.2.1. 디자인 목표

1. 첫 화면에서 가이드의 목적, 대상, 예상 시간, 준비물을 이해한다.
2. 현재 단계와 전체 진행 상태를 항상 파악할 수 있다.
3. 경고와 파괴적 작업을 일반 설명보다 명확하게 구분한다.
4. 단계마다 “무엇을 한다 → 어떻게 확인한다 → 실패하면 어디를 본다”의 순서를 유지한다.
5. 모바일에서도 명령어 복사, 체크, 분기 선택, 다음 단계 이동을 안정적으로 수행한다.
6. 다크·라이트·인쇄 환경에서 같은 정보 계층을 유지한다.
7. 작성 화면과 내보낸 리더 화면의 결과 차이를 최소화한다.

#### 1.2.2. 디자인 비목표

- 장식적 애니메이션과 시각 효과를 통한 체류 시간 증가
- 소셜 피드형 탐색이나 공개 문서 추천
- 복잡한 노코드 빌더처럼 모든 설정을 한 화면에 노출
- 문서별 과도한 자유 테마 및 임의 CSS 편집
- 긴 형식의 위키·블로그·노트 앱 대체

#### 1.2.3. 핵심 사용자 페르소나

**A. 설명을 반복하는 개인 작성자**

- 가족이나 지인에게 PC·스마트폰 작업을 자주 설명한다.
- 전문 문서 도구보다 빠른 폼 입력을 선호한다.
- 상대가 어느 단계에서 막혔는지 쉽게 확인하고 싶다.

**B. 고객 지원 담당자**

- 동일 문의에 대해 매번 다른 표현으로 답변하는 비용을 줄이고 싶다.
- 데이터 삭제·계정 잠금 같은 경고를 누락하면 안 된다.
- 오류 상황별 분기와 대체 절차가 필요하다.

**C. 기술 문서 작성자·개발자**

- 기존 Markdown을 재사용하고 싶다.
- 배포처에 종속되지 않는 HTML 파일이 필요하다.
- 코드, 명령어, 링크, 이미지의 정확한 표현이 중요하다.

**D. 비전문가 독자**

- 기술 용어를 잘 모르며 모바일로 가이드를 본다.
- 지금 해야 할 일과 성공 여부만 빠르게 확인하고 싶다.
- 실패했을 때 전체 문서를 다시 읽지 않고 해결책을 찾고 싶다.

### 1.3. 핵심 차별점 (Key Differentiators)

1. **한 단계씩(One Step at a Time)**  
   독자 화면은 현재 단계에 시각적 우선권을 부여하고, 이전·다음 단계는 보조 정보로 다룬다. 전체 절차를 한꺼번에 읽게 하지 않는다.

2. **실패 안전성(Failure-aware)**  
   경고, 성공 기준, 오류 해결을 일반 본문과 명확히 분리한다. 사용자는 실행 전 위험을 확인하고, 실행 후 성공을 체크하며, 실패했을 때 현재 맥락에서 해결책을 펼친다.

3. **편집과 결과의 일치(Author–Reader Fidelity)**  
   작성기 미리보기와 내보낸 HTML은 동일한 콘텐츠 렌더러와 디자인 토큰을 사용한다. 작성자가 본 결과와 독자가 받는 결과의 차이를 줄인다.

4. **종이 매뉴얼의 안정감 + 앱의 진행성**  
   넓은 여백, 명확한 번호, 절제된 선과 카드로 문서의 신뢰감을 주되, 체크박스·진행률·분기로 앱처럼 반응한다.

### 1.4. 디자인 원칙

#### 원칙 1. 다음 행동이 가장 먼저 보인다

각 화면에서 주요 CTA는 하나만 우선 강조한다. 현재 단계 완료 전에는 “다음”보다 성공 체크가 우선이며, 경고 확인 전에는 시작 버튼이 비활성화된다.

#### 원칙 2. 위험은 숨기지 않고 과장하지 않는다

경고는 심각도별 색상·아이콘·문구를 함께 사용한다. 빨간색은 데이터 삭제, 계정 잠금, 장치 손상처럼 실제 위험에만 사용한다.

#### 원칙 3. 읽기보다 수행을 돕는다

한 단계에는 하나의 핵심 목표를 둔다. 긴 설명은 소제목, 목록, 코드, 이미지로 나누고 오류 해결은 기본 접힘 상태로 둔다.

#### 원칙 4. 완료 기준을 문장으로 쓴다

“완료”라는 추상 라벨 대신 “PC에서 Discord에 로그인되었습니다”처럼 사용자가 관찰할 수 있는 상태를 체크박스 라벨로 사용한다.

#### 원칙 5. 접근성이 시각 스타일보다 우선한다

색상만으로 상태를 구분하지 않고, 16px 미만 본문을 사용하지 않으며, 모든 상호작용은 키보드와 스크린 리더로 수행 가능해야 한다.

## 2. 상세 기능 요구사항 (Detailed Requirements)

### 2.1. 레이아웃 및 인터페이스 (Layout & Interface)

#### 2.1.1. 전체 뷰 정책

- **레이아웃 방식**: Container-based + Fluid
- **기본 방향**: Mobile First
- **페이지 배경**: 약한 중성 배경
- **콘텐츠 표면**: 흰색 또는 어두운 중성 카드
- **최대 본문 폭**: 리더 760px, 편집 중앙 열 800px
- **읽기 줄 길이**: 한 줄 약 45~75자 범위 유지
- **가로 스크롤**: 코드 블록을 제외하고 금지

#### 2.1.2. 데스크톱 작성 화면

1024px 이상에서는 세 영역을 사용한다.

```text
┌────────────────────────────────────────────────────────────────────┐
│ Logo / Guide title / Save state       Preview  Export  Theme      │
├───────────────┬────────────────────────────────┬───────────────────┤
│ Guide outline │ Main editor                    │ Inspector / QA    │
│ 240–280px     │ 640–800px                      │ 280–320px         │
│               │                                │                   │
│ Intro         │ Selected section form          │ Validation        │
│ Preparation   │ Blocks                         │ Branch summary    │
│ Warnings      │                                │ Export readiness  │
│ Steps         │                                │                   │
└───────────────┴────────────────────────────────┴───────────────────┘
```

- 헤더는 높이 64px의 sticky 영역이다.
- 왼쪽 개요는 단계 탐색과 재정렬에 사용한다.
- 중앙 편집기는 선택한 섹션 하나에 집중한다.
- 오른쪽 패널은 필드 속성, 분기 연결, 검증 결과를 상황에 따라 전환한다.
- 1280px 미만에서는 오른쪽 패널을 접고 필요할 때 드로어로 연다.

#### 2.1.3. 태블릿 작성 화면

640~1023px에서는 다음 구조를 사용한다.

- 상단 헤더
- 접이식 개요 드로어
- 단일 중앙 편집 열
- 하단 또는 우측 슬라이드형 속성 패널
- 미리보기는 전체 화면 오버레이 또는 별도 라우트

#### 2.1.4. 모바일 작성 화면

360~639px에서는 작성 기능을 유지하되 복잡한 다중 패널을 제거한다.

- 상단: 뒤로, 문서명, 저장 상태, 더보기
- 본문: 선택한 섹션 편집
- 하단 고정 바: 개요, 블록 추가, 미리보기
- 단계 재정렬: 드래그보다 “위로/아래로 이동” 버튼 우선
- 분기 편집: 조건·대상 단계를 순차 폼으로 표시
- 긴 설정은 아코디언으로 접는다.

#### 2.1.5. 리더 화면

리더는 모든 화면에서 단일 열을 기본으로 한다.

```text
┌─────────────────────────────────────┐
│ HowSheet        3 / 7  [Theme] [⋯] │  Sticky header
├─────────────────────────────────────┤
│ Guide title                         │
│ Audience · Estimated time           │
│ Summary                             │
├─────────────────────────────────────┤
│ Step 3                              │
│ 단계 제목                           │
│ 설명 / 이미지 / 명령어             │
│                                     │
│ [문제 해결 보기]                    │
│                                     │
│ □ 성공 기준 문장                    │
├─────────────────────────────────────┤
│ [이전]                 [다음 단계]  │  Mobile sticky action bar
└─────────────────────────────────────┘
```

- 모바일에서 헤더와 하단 행동 바는 sticky로 유지한다.
- 데스크톱에서는 좌측에 선택형 전체 개요를 표시할 수 있다.
- 현재 단계 카드 외의 단계는 기본적으로 축약 표시하거나 개요에서만 보인다.
- 준비물과 필수 경고를 완료하기 전에는 단계 실행 화면으로 넘어가지 않는다.

#### 2.1.6. 테마 정책

- **지원**: Light / Dark / System Preference
- **기본값**: System Preference
- **리더**: 작성자가 테마 전환 허용 여부를 설정
- **인쇄**: 항상 라이트 인쇄 테마 사용
- **색상 모드 전환**: 즉시 적용, 페이지 재로드 없음
- **플래시 방지**: 문서 렌더링 전에 저장된 테마 속성 적용

### 2.2. 사용자 상호작용 (Interaction Logic)

#### 2.2.1. 작성기의 주요 액션

**새 가이드 생성**

- 대시보드의 가장 강한 CTA로 배치한다.
- 클릭 시 빈 문서, Markdown 가져오기, 샘플 템플릿 중 선택한다.
- 기본 문서는 첫 단계가 이미 생성된 상태로 연다.

**단계 추가**

- 현재 단계 아래의 `+ 단계 추가` 버튼과 개요 하단 버튼을 제공한다.
- 새 단계 생성 후 제목 입력으로 포커스를 이동한다.
- 토스트보다 개요에서 새 항목을 잠시 강조해 위치를 알려준다.

**블록 추가**

- 텍스트, 명령어, 링크, 이미지, 체크리스트, 선택 분기를 아이콘+텍스트로 표시한다.
- 최근 사용 블록을 상단에 재배치하지 않고 고정 순서를 유지해 학습 비용을 줄인다.

**재정렬**

- 데스크톱: 드래그 핸들 제공
- 키보드·모바일: 위로/아래로 이동 버튼 제공
- 이동 후 “4단계 중 2번째로 이동됨”을 라이브 영역에 알린다.

**삭제**

- 휴지통 아이콘만 단독 노출하지 않고 `단계 삭제` 텍스트를 함께 제공한다.
- 분기에서 참조되는 단계는 삭제 전 영향 범위를 보여준다.
- 삭제 확인 대화상자의 주요 버튼은 위험 색상이며, 취소 버튼에 초기 포커스를 둔다.

**미리보기**

- 작성 중 언제든 열 수 있지만 저장 완료를 기다리지 않는다.
- 현재 메모리 스냅샷으로 즉시 렌더링한다.
- 미리보기 상단에는 `편집기로 돌아가기`와 현재 기기 폭 선택을 제공한다.

**내보내기**

- 검증 오류가 있으면 버튼은 열 수 있으나 최종 다운로드가 비활성화된다.
- 오류 수, 경고 수, 예상 파일 크기, 외부 자원 0건 여부를 한 화면에 표시한다.

#### 2.2.2. 리더의 주요 액션

**이어하기**

- 이전 진행 상태가 있을 때 시작 화면에서 두 선택을 제공한다.
  - `3단계부터 이어하기` - Primary
  - `처음부터 시작` - Secondary

**준비물 확인**

- 필수 준비물은 모두 체크해야 시작 버튼이 활성화된다.
- 선택 준비물은 `선택` 배지를 표시한다.

**경고 확인**

- 필수 경고는 강조 카드와 확인 체크박스로 표시한다.
- 데이터 삭제 등 위험 단계는 체크 라벨에 결과를 구체적으로 쓴다.
- 여러 경고가 있을 때 한 번의 전체 동의로 축약하지 않는다.

**명령어 복사**

- 코드 우측 상단에 `복사` 버튼을 둔다.
- 성공 시 2초 동안 `복사됨`으로 바뀐다.
- 실패 시 코드 선택과 수동 복사 안내를 제공한다.

**단계 완료**

- 체크박스는 카드 하단의 독립 영역에 둔다.
- 체크 후 다음 단계 버튼이 활성화된다.
- `automatic` 단계는 필요한 행동 후 즉시 다음으로 넘어가지 않고 짧은 상태 메시지를 제공한다.

**분기 선택**

- 질문 아래에 큰 라디오 카드로 선택지를 배치한다.
- 선택과 다음 단계 이동을 분리해 실수로 경로가 바뀌지 않게 한다.
- 선택 변경 시 이후 진행 상태가 달라질 수 있음을 알린다.

**오류 해결**

- `이 단계에서 문제가 생겼나요?` 트리거를 제공한다.
- 증상 목록을 먼저 보여주고, 선택하면 원인과 해결 방법을 펼친다.
- 해결 후 현재 단계로 돌아갈 수 있는 앵커를 제공한다.

**진행 초기화**

- 설정 메뉴 안에 배치하고 즉시 실행하지 않는다.
- 초기화 범위와 되돌릴 수 없음을 확인한다.

#### 2.2.3. Hover / Focus / Press 상태

- Hover는 배경색 또는 테두리 변화 정도로 제한한다.
- 링크는 hover 시 밑줄을 강화한다.
- 모든 포커스 가능한 요소는 2px 이상의 명확한 포커스 링을 가진다.
- `:focus-visible`을 사용해 마우스 클릭 시 불필요한 링을 줄인다.
- Press 상태는 1px 이동 또는 배경 농도 변화로 표현하되 레이아웃 점프를 만들지 않는다.
- Disabled 상태는 투명도만 낮추지 않고 커서·설명 문구로 이유를 제공한다.

#### 2.2.4. 모션

- 기본 전환: 120ms
- 패널·아코디언: 180ms
- 모달: 200ms 이하
- 단계 전환은 8~12px 이동과 페이드 수준으로 제한
- `prefers-reduced-motion: reduce`에서는 모든 비필수 전환 제거
- 성공 시 폭죽, 파티클 등 주의를 분산하는 효과는 사용하지 않는다.

### 2.3. 데이터 구조 및 모듈 (Component Structure)

#### 2.3.1. 헤더 (Header)

**작성기 헤더 구성**

- 좌측: HowSheet 워드마크, 대시보드로 이동
- 중앙: 현재 가이드 제목, 저장 상태
- 우측: 미리보기, 내보내기, 테마, 더보기

**리더 헤더 구성**

- 좌측: HowSheet 또는 가이드 제목 축약
- 중앙/우측: 현재 단계와 진행률
- 우측: 테마, 설정

헤더는 스크롤 중에도 현재 문맥을 잃지 않도록 sticky로 유지한다.

#### 2.3.2. 네비게이션 (Navigation)

- 작성기 데스크톱: 좌측 개요 패널
- 작성기 모바일: 전체 화면 바텀 시트/드로어
- 리더 데스크톱: 선택적 단계 개요
- 리더 모바일: 전체 개요는 설정 메뉴에서 연다.
- 현재 항목은 색상, 좌측 막대, `aria-current`로 구분한다.
- 완료 단계는 체크 아이콘과 `완료` 텍스트를 함께 제공한다.

#### 2.3.3. 콘텐츠 영역 (Content)

- 편집 폼은 섹션별 카드보다 큰 단일 작업 표면을 사용해 중첩 카드 남발을 피한다.
- 리더는 단계 자체를 가장 큰 카드로 사용한다.
- 코드와 이미지는 본문 폭을 최대한 활용한다.
- 이미지 캡션은 이미지 바로 아래에 14px 보조 텍스트로 둔다.
- 오류 해결은 단계 카드 안의 구분된 접이식 영역으로 배치한다.

#### 2.3.4. 푸터 (Footer)

- 작성기 대시보드: 버전, 데이터 저장 위치 안내, 개인정보 정책 링크
- 리더: `Made with HowSheet`, 가이드 개정 번호, 마지막 업데이트일
- 독립 HTML에서는 외부 링크를 강제하지 않으며 작성자가 브랜딩 표시를 끌 수 있는 확장은 MVP 이후 검토

### 2.4. 화면별 UX 명세

#### 2.4.1. 로컬 대시보드

**목적**: 저장된 가이드를 찾고 생성·가져오기·백업한다.

**구성**

1. 상단 로고와 테마 전환
2. `새 가이드 만들기` Primary CTA
3. `JSON 가져오기`, `Markdown 가져오기` Secondary 액션
4. 최근 수정 순 가이드 카드
5. 로컬 저장 안내
6. 전체 데이터 백업·초기화 메뉴

**가이드 카드 정보**

- 제목
- 대상 사용자 요약
- 단계 수
- 마지막 수정 시간
- 검증 상태
- 열기, 복제, 내보내기, 삭제

**빈 상태**

- “아직 만든 가이드가 없습니다”
- 활용 예시 3개
- 새 가이드 CTA

#### 2.4.2. 가이드 기본 정보 화면

**필드 순서**

1. 가이드 제목
2. 한 줄 요약
3. 대상 사용자
4. 예상 소요 시간
5. 작성자·언어
6. 기본 테마와 독자 설정

제목 입력 아래에는 실제 리더의 제목 미리보기를 작게 보여준다.

#### 2.4.3. 준비물 편집 화면

- 항목을 행 단위로 편집한다.
- 필수/선택 토글을 명확히 표시한다.
- 링크와 상세 설명은 확장 영역에서 입력한다.
- 빈 준비물 섹션도 허용하지만 리더에서는 자동 숨김 처리한다.

#### 2.4.4. 경고 편집 화면

- 심각도 선택: 안내, 주의, 위험
- 제목과 본문
- 독자 확인 필수 여부
- 확인 라벨
- 미리보기 카드

위험 경고 선택 시 “빨간색은 실제 데이터 손실·장치 손상 위험에만 사용”이라는 도움말을 표시한다.

#### 2.4.5. 단계 편집 화면

```text
[단계 3] [위로] [아래로] [복제] [삭제]

단계 제목 __________________________________
짧은 설명 __________________________________

콘텐츠
┌──────────────────────────────────────────┐
│ Text block                               │
├──────────────────────────────────────────┤
│ Code block                         ↕  ⋯ │
├──────────────────────────────────────────┤
│ Image block                        ↕  ⋯ │
└──────────────────────────────────────────┘
[+ 텍스트] [+ 명령어] [+ 링크] [+ 이미지] [+ 선택]

성공 기준 __________________________________
□ 선택 사항인 단계

다음 단계 / 조건 분기 ______________________
관련 오류 해결 _____________________________
```

- 콘텐츠 블록은 외곽선과 타입 라벨로 구분한다.
- 블록 도구 모음은 선택된 블록에만 노출한다.
- 단계 번호는 데이터 순서에서 자동 계산하며 직접 입력하지 않는다.

#### 2.4.6. 분기 편집 화면

- 상단에 간단한 문장식 요약을 보여준다.
  - “선택이 ‘이메일을 알고 있음’이면 → 4단계로 이동”
- 조건, 값, 대상 단계를 한 행에 억지로 압축하지 않는다.
- 분기 규칙마다 우선순위를 표시한다.
- 기본 경로는 별도 `그 외의 경우` 카드로 둔다.
- 순환·누락·도달 불가 오류는 해당 대상 선택 바로 아래에 표시한다.
- 전체 그래프 시각화는 MVP 필수가 아니며 텍스트 경로 요약으로 대체한다.

#### 2.4.7. Markdown 가져오기 검토 화면

**2단 구조**

- 좌측/상단: 원본 Markdown 개요
- 우측/하단: HowSheet 매핑 결과

각 섹션에는 상태 배지를 표시한다.

- 초록 `자동 매핑`
- 주황 `검토 필요`
- 회색 `일반 본문으로 유지`

사용자는 단계 경계, 준비물, 오류 해결 섹션을 재지정한 뒤 가져오기를 완료한다.

#### 2.4.8. 미리보기 화면

- 리더와 동일한 컴포넌트 사용
- 상단에 편집기 전용 미리보기 바 표시
- 기기 폭 프리셋: 390, 768, 1280px
- 진행 상태 초기화 버튼
- 경로 시뮬레이션 결과와 검증 경고 표시

#### 2.4.9. 내보내기 대화상자

**정보 순서**

1. 형식 선택: JSON / 단일 HTML / 인쇄
2. 파일명
3. 내보내기 검사 상태
4. 예상 파일 크기와 이미지 비중
5. 옵션: 전체 개요, 테마 전환, 진행 초기화 허용, 인쇄 경로
6. 다운로드 CTA

오류가 있으면 상단에 첫 오류와 전체 개수를 보여주고 `오류 수정하러 가기`를 주요 액션으로 바꾼다.

#### 2.4.10. 리더 시작 화면

- 제목
- 한 줄 요약
- 대상 사용자
- 예상 시간
- 준비물 체크
- 경고 확인
- 시작 또는 이어하기 CTA

시작 화면에서는 전체 단계 내용을 노출하지 않는다. 필요한 경우 단계 수와 주요 섹션 개요만 제공한다.

#### 2.4.11. 리더 단계 화면

단계 카드 내부 순서는 고정한다.

1. 단계 번호와 제목
2. 짧은 설명
3. 텍스트·이미지·명령어·링크·체크리스트
4. 분기 질문
5. 오류 해결
6. 성공 기준 체크
7. 다음 행동

독자가 성공 체크를 하지 않았는데 다음을 누르면 상단 오류가 아니라 체크 영역 근처에 이유를 표시한다.

#### 2.4.12. 완료 화면

- 성공 아이콘
- 완료 제목과 메시지
- 완료한 필수 단계 수
- 시작·완료 시간 또는 소요 시간(로컬에서 계산 가능한 경우)
- 인쇄/PDF 저장
- 관련 링크
- 처음부터 다시 시작

완료 화면은 축하 효과보다 “무엇이 완료되었고 다음에 무엇을 확인할지”를 우선한다.

### 2.5. 출력 및 결과물 (Output)

- React 컴포넌트 기반 편집기
- 독립 번들 리더 컴포넌트
- CSS Custom Properties 디자인 토큰
- 반응형 작성기·리더 화면
- 인쇄 전용 스타일
- 라이트·다크 테마
- 키보드·스크린 리더 접근성 상태

#### 디자인 QA 기준

- 320px에서 가로 스크롤 없음
- 200% 확대 시 기능 손실 없음
- 44×44px 최소 터치 영역
- 라이트·다크 주요 텍스트 대비 AA 수준
- 포커스 링이 모든 인터랙션에서 보임
- 색상 없이도 오류·경고·완료 상태 식별 가능
- 이미지 누락, 긴 URL, 긴 명령어, 100자 제목에서도 레이아웃 붕괴 없음
- 인쇄 시 sticky 요소, 버튼, 토스트 미출력

## 3. 기술 스택 및 라이브러리 (Tech Stack)

### 3.1. Core

- **Frontend Framework**: React + TypeScript
- **Styling Engine**: CSS Modules + CSS Custom Properties
- **Build Tool**: Vite
- **Icon System**: Lucide 기반 선형 아이콘 또는 동등한 SVG 아이콘
- **Form UI**: React Hook Form과 네이티브 입력 요소
- **Animation**: CSS transition 우선, 별도 모션 라이브러리 사용하지 않음
- **Print**: 전용 `@media print` 스타일

### 3.2. Libraries & Tools

1. **CSS Modules**
   - 컴포넌트 범위 스타일
   - 편집기와 리더 클래스 충돌 방지
   - 전역 스타일은 reset, tokens, typography, print로 제한

2. **CSS Custom Properties**
   - 라이트·다크·인쇄 토큰 공유
   - 내보낸 HTML에도 동일 변수명 사용
   - 가이드별 임의 색상보다 제한된 브랜드 변형만 허용

3. **Lucide Icons**
   - 단계 완료, 경고, 정보, 복사, 이동, 내보내기 등의 선형 아이콘
   - 아이콘 단독 사용을 최소화하고 텍스트 라벨 병행
   - 내보낸 HTML에는 필요한 SVG만 인라인

4. **Storybook 또는 동등한 컴포넌트 카탈로그(선택)**
   - 상태별 컴포넌트 검토
   - 라이트·다크·모바일·긴 콘텐츠 케이스
   - 디자인 QA와 시각 회귀 테스트 기준 제공

5. **Playwright Visual Comparison**
   - 주요 화면의 반응형 스냅샷
   - 테마·오류·완료·인쇄 상태 회귀 확인

### 3.3. 스타일링 규칙

- 클래스명은 CSS Modules의 지역 범위를 사용한다.
- 전역 유틸리티 클래스는 `sr-only`, `focus-ring`, `print-only` 정도로 제한한다.
- 인라인 스타일은 동적 진행률과 계산 치수에만 사용한다.
- `!important`는 인쇄에서 인터랙션 UI를 숨기는 경우 외 사용하지 않는다.
- 디자인 토큰을 거치지 않은 임의 색상·간격 값 사용을 금지한다.
- 작성기와 리더가 공유하는 콘텐츠 컴포넌트는 같은 토큰과 마크업 구조를 사용한다.

#### 4.1.2. 정보 우선순위

리더 단계 카드의 시각 우선순위는 다음 순서를 유지한다.

1. 단계 번호·제목
2. 위험 경고 또는 필수 행동
3. 실행 설명과 명령어
4. 성공 기준
5. 다음 단계 CTA
6. 오류 해결과 보조 메타데이터

1. 현재 편집 섹션
2. 필수 필드와 오류
3. 콘텐츠 편집
4. 분기·고급 설정
5. 보조 도움말

### 4.2. 반응형 로직 (Responsive Logic)

#### 4.2.1. Wide Desktop - 1440px 이상

- 좌측 280px, 중앙 최대 800px, 우측 320px
- 패널 사이 24px 간격
- 리더는 좌측 개요 240px + 본문 760px 구성 가능

#### 4.2.2. Desktop - 1024~1439px

- 좌측 240px, 중앙 유동 폭
- 우측 검사 패널은 1280px 미만에서 드로어
- 헤더 액션 라벨 유지

#### 4.2.3. Tablet - 640~1023px

- 단일 중앙 열
- 개요와 검사 패널을 드로어로 전환
- 헤더의 보조 액션은 더보기 메뉴로 이동
- 카드 패딩 24px

#### 4.2.4. Mobile - 0~639px

- 전체 폭 단일 열
- 페이지 좌우 패딩 16px, 360px 미만은 12px
- 카드 패딩 20px 또는 16px
- 하단 sticky action bar 사용
- 버튼은 중요도에 따라 세로 스택 가능
- 단계 제목 20px 이상
- 코드 블록만 내부 가로 스크롤 허용
- 테이블형 정보는 카드 또는 정의 목록으로 변환

#### 4.2.5. Height 대응

- 모바일 주소창 변동 대응에 `min-height: 100dvh` 사용
- 지원되지 않는 환경에는 `100vh` 폴백
- 모달은 화면 전체 높이보다 길 경우 내부 스크롤
- 하단 행동 바 높이만큼 본문 `padding-bottom` 확보

### 4.3. 핵심 컴포넌트 로직 (Core Components)

#### 4.3.1. Step Card

**구조**

```text
Step label → Title → Summary → Content blocks
→ Decision(optional) → Troubleshooting → Success check → Actions
```

**상태**

- `upcoming`: 중성 테두리
- `current`: 브랜드 테두리와 단계 배지
- `completed`: 성공 아이콘·라벨
- `blocked`: 경고 아이콘과 차단 이유
- `skipped`: 낮은 대비, 경로에서 제외됨 라벨

현재 단계 카드에만 강한 그림자 또는 브랜드 외곽선을 사용한다.

#### 4.3.2. Warning Card

| 심각도  | 아이콘   | 라이트 배경 | 텍스트/테두리 | 사용 예                           |
| ------- | -------- | ----------- | ------------- | --------------------------------- |
| Info    | 원형 i   | 옅은 파랑   | 파랑          | 참고, 권장 사항                   |
| Warning | 삼각형 ! | 옅은 주황   | 갈색/주황     | 설정 변경, 일시 중단 가능성       |
| Danger  | 팔각형 ! | 옅은 빨강   | 진한 빨강     | 데이터 삭제, 계정 잠금, 장치 손상 |

- 제목, 본문, 확인 체크 영역을 분리한다.
- 아이콘만으로 심각도를 전달하지 않는다.
- Danger는 한 화면에 과도하게 반복하지 않는다.

#### 4.3.3. Success Checkbox

- 기본 체크박스보다 큰 24px 컨트롤
- 전체 성공 기준 문장이 클릭 영역
- 카드 하단에 별도 배경 영역
- 체크 시 상태 아이콘과 `완료됨` 라벨 표시
- 애니메이션은 120ms 이하의 색상·아이콘 전환만 사용

#### 4.3.4. Decision Option Card

- 라디오 버튼 + 제목 + 선택적 설명
- 카드 전체가 클릭 영역
- 선택 상태는 브랜드 테두리, 선택 아이콘, 배경 농도로 구분
- 2열 배치는 각 옵션이 짧고 768px 이상일 때만 허용
- 선택지 문장이 길면 항상 1열

#### 4.3.5. Troubleshooting Accordion

- 트리거: `이 단계에서 문제가 생겼나요?`
- 열었을 때 증상 목록을 먼저 표시
- 개별 항목은 증상 → 가능한 원인 → 해결 순서
- 해결 안 됨 상태는 별도 지원 링크가 있을 때만 표시
- 여러 아코디언을 동시에 열 수 있으나 모바일에서는 현재 항목 우선

#### 4.3.6. Code Block

- 배경은 높은 대비의 중성 색상
- 언어 또는 `명령어` 라벨
- 복사 버튼은 우측 상단
- 긴 줄은 기본 가로 스크롤, 사용자가 줄바꿈 전환 가능
- 명령어와 출력 예시는 시각적으로 구분
- 인쇄 시 복사 버튼 제거, 줄이 너무 길면 `overflow-wrap:anywhere` 적용 가능

#### 4.3.7. Progress Header

- `3 / 7 단계` 텍스트와 진행 막대
- 분기 전에는 전체가 확정되지 않았을 수 있으므로 `현재 경로 기준` 보조 문구 사용
- 막대 높이 4~6px
- 색상만이 아니라 숫자를 항상 표시

#### 4.3.8. Validation Panel

- 그룹: 오류, 경고, 개선 제안
- 각 항목에 필드 경로와 짧은 해결 문구 표시
- 클릭 시 해당 필드로 스크롤하고 포커스 이동
- 오류 0건이면 단순 성공 메시지와 내보내기 준비 상태 표시
- 초록색 대형 배너 남발 대신 작은 상태 요약 사용

### 4.4. 사용자 흐름

#### 4.4.1. 신규 작성 흐름

```text
대시보드
→ 새 가이드
→ 기본 정보
→ 준비물·경고
→ 단계 작성
→ 분기·오류 해결
→ 미리보기
→ 검증
→ HTML 내보내기
```

각 단계 상단에는 완료 여부를 보여주는 작은 제작 진행 표시를 제공할 수 있으나, 강제 마법사 방식으로 잠그지 않는다.

#### 4.4.2. 독자 진행 흐름

```text
가이드 소개
→ 준비물 체크
→ 필수 경고 확인
→ 현재 단계 수행
→ 성공 체크
→ 분기 선택(필요 시)
→ 다음 단계
→ 완료 화면
```

독자가 뒤로 이동할 수 있으며, 이전 분기 선택을 바꾸면 이후 경로 변경 안내를 표시한다.

#### 4.4.3. 오류 해결 흐름

```text
단계 수행 실패
→ 문제 해결 열기
→ 증상 선택
→ 원인/해결 확인
→ 단계로 돌아가기
→ 성공 체크
```

오류 해결을 별도 페이지로 이동시키지 않아 현재 단계 문맥을 유지한다.

### 5.2. 타이포그래피 (Typography)

#### 5.2.1. Font Family

```css
--font-sans:
  system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', 'Apple SD Gothic Neo', 'Noto Sans KR',
  sans-serif;

--font-mono: ui-monospace, SFMono-Regular, Consolas, 'Liberation Mono', monospace;
```

독립 HTML이 외부 웹폰트에 의존하지 않도록 시스템 폰트를 기본으로 한다.

#### 5.2.2. Font Weight

- Regular: 400
- Medium: 500
- Semibold: 600
- Bold: 700
- Display 강조: 750 또는 브라우저가 지원하는 가장 가까운 값

본문에서 700 굵기를 남발하지 않고, 단계 제목·경고 제목·주요 버튼에 제한한다.

#### 5.2.3. 한국어 문장 규칙

- 본문은 `word-break: keep-all`을 우선 사용한다.
- 좁은 화면과 긴 URL에서는 `overflow-wrap: anywhere`를 보조 적용한다.
- 조사 하나가 다음 줄에 단독으로 남는 현상을 완전히 통제하려 하지 않는다.
- 영문·숫자·명령어는 코드 폰트 또는 적절한 띄어쓰기로 구분한다.

### 5.3. 간격 시스템 (Spacing)

### 5.4. 모서리·테두리·그림자

- 입력·버튼: 8px
- 작은 카드·알림: 10px
- 단계 카드·모달: 16px
- pill 배지: 999px
- 기본 테두리: 1px
- 현재 단계 강조: 2px 또는 내부 outline
- 그림자는 계층을 만들 때만 사용하며, 테두리와 동시에 과하게 쓰지 않는다.

```css
--shadow-sm: 0 1px 2px rgb(15 23 42 / 0.06);
--shadow-md: 0 8px 24px rgb(15 23 42 / 0.1);
```

다크 모드에서는 그림자보다 밝은 테두리와 표면 차이를 우선한다.

### 5.5. 아이콘 시스템

- 기본 크기: 18px
- 작은 메타: 16px
- 주요 상태: 20~24px
- 선 굵기: 1.75~2px
- 아이콘 단독 버튼은 최소 44×44px
- 장식 아이콘은 `aria-hidden="true"`
- 의미 아이콘은 텍스트 또는 접근성 라벨과 결합

주요 아이콘:

- 체크: 완료
- 삼각형 느낌표: 주의
- 팔각형 느낌표: 위험
- 원형 i: 정보
- 복사: 명령어 복사
- 갈래 화살표: 분기
- 렌치: 문제 해결
- 파일 내보내기: HTML/JSON 내보내기
- 프린터: PDF/인쇄

### 5.6. 컴포넌트 규격

#### 5.6.1. Button

| Size   | 높이 | 좌우 패딩 | 글자 크기 |
| ------ | ---: | --------: | --------: |
| Small  | 36px |      12px |      14px |
| Medium | 44px |      16px |   15~16px |
| Large  | 52px |      20px |      16px |

- 모바일 주요 CTA는 Medium 이상
- Primary, Secondary, Ghost, Danger 네 변형
- 한 화면에 Primary 버튼이 여러 개 경쟁하지 않게 한다.

#### 5.6.2. Input

- 최소 높이 44px
- 좌우 패딩 12~14px
- 라벨과 입력 사이 8px
- 도움말과 오류는 입력 아래 6px
- 필수 표시는 별표만 쓰지 않고 접근성 텍스트 제공

#### 5.6.3. Checkbox / Radio

- 컨트롤 시각 크기 20~24px
- 전체 라벨 행 최소 높이 44px
- 체크·선택 상태는 아이콘, 배경, 테두리로 표현
- 긴 성공 기준은 2~3줄을 허용

#### 5.6.4. Badge

- 높이 24~28px
- 글자 12~13px, Semibold
- 단계 상태, 필수/선택, 자동 매핑 상태에 사용
- 본문 핵심 메시지를 배지 안에 넣지 않는다.

#### 5.6.5. Card

- 모바일 패딩: 16~20px
- 데스크톱 패딩: 24~32px
- 카드 간격: 16~24px
- 카드 중첩은 최대 2단계
- 경고·코드·오류 해결은 같은 단계 카드 안에서 독립 배경으로 구분

### 5.7. 폼 콘텐츠 작성 규칙

작성기 도움말과 샘플 문구는 쉬운 한국어를 사용한다.

**좋은 단계 제목**

- `등록된 이메일 주소 확인하기`
- `NVMe 파티션을 ext4로 포맷하기`
- `앱 권한에서 알림 허용하기`

**피해야 할 단계 제목**

- `설정`
- `다음 단계`
- `처리하기`

**좋은 성공 기준**

- `PC 화면에 Discord 채널 목록이 표시됩니다.`
- `findmnt /mnt/nvme` 결과에 `/dev/nvme0n1p1`이 표시됩니다.

**피해야 할 성공 기준**

- `완료했습니다.`
- `정상입니다.`

### 5.8. 상태·피드백 메시지

#### 저장 상태

- `저장 중…`
- `모든 변경사항이 이 브라우저에 저장되었습니다.`
- `저장하지 못했습니다. JSON으로 백업한 뒤 다시 시도하세요.`

#### 검증 상태

- `내보낼 준비가 되었습니다.`
- `오류 2개를 수정해야 HTML로 내보낼 수 있습니다.`
- `도달할 수 없는 단계가 1개 있습니다.`

#### 진행 상태

- `3 / 7 단계 · 현재 경로 기준`
- `이 단계를 완료하면 다음으로 이동할 수 있습니다.`
- `선택을 변경하면 이후 진행 경로가 바뀝니다.`

#### 로컬 저장 안내

- `진행 상태는 이 브라우저에만 저장됩니다.`
- `시크릿 모드나 브라우저 데이터 삭제 후에는 복원되지 않을 수 있습니다.`

### 5.9. 빈 상태·오류 상태

#### 이미지 없음

- 회색 플레이스홀더와 `이미지를 불러오지 못했습니다` 문구
- 대체 텍스트가 있으면 본문으로 표시
- 작성기에서는 자산 다시 연결 CTA 제공

#### 단계 없음

- 편집기: 첫 단계 만들기 CTA
- 리더: 잘못된 가이드 오류 화면, 원본 작성자에게 문의 안내

#### 저장소 사용 불가

- 상단 지속 배너
- 자동 저장 대신 수동 JSON 백업 CTA
- 작업을 막지는 않되 새로고침 위험을 명확히 표시

#### 손상된 내보내기 파일

- 기술 오류 코드보다 사용자가 할 행동을 먼저 표시
- `이 파일의 가이드 데이터를 읽을 수 없습니다.`
- `파일을 다시 내보내거나 작성자에게 새 파일을 요청하세요.`

### 5.10. 인쇄 디자인

- A4 세로 기본
- 페이지 여백 14~18mm
- 제목·대상·작성일·개정 번호를 첫 페이지에 표시
- 단계 카드는 인쇄에서 그림자를 제거하고 얇은 테두리 사용
- 체크박스는 빈 사각형 또는 체크 상태로 인쇄
- 숨겨진 아코디언 내용도 인쇄 옵션에 따라 펼침
- 링크 URL은 본문 뒤에 작은 크기로 표시 가능
- 비디오·인터랙션 전용 요소는 설명 텍스트로 대체
- 페이지 중간에서 경고 제목과 본문이 분리되지 않게 한다.

## 6. 파일 구조 (File Structure)

파일 구조는 이 문서에서 정의하지 않는다. **`docs/File_Structure.md`를 기준 문서로 사용한다.**

디자인 백서와 기술 백서가 각각 다른 트리를 유지하면 그룹 이름, 컴포넌트 이름, 스타일 파일 구성이 서로 어긋나 구현 중 드리프트가 발생한다. 두 백서의 파일 구조를 하나로 통합해 `docs/File_Structure.md`로 분리했다.

해당 문서에서 확인할 내용:

| 찾는 것                                                                             | 위치                     |
| ----------------------------------------------------------------------------------- | ------------------------ |
| `src/` 전체 트리와 컴포넌트 그룹(`ui` / `layout` / `content` / `editor` / `reader`) | `File_Structure.md` §2   |
| `styles/` 파일 구성과 토큰 파일 위치                                                | `File_Structure.md` §2.1 |
| 테마 처리 위치와 플래시 방지 코드 배치                                              | `File_Structure.md` §2.3 |
| 편집기–리더 경계, 콘텐츠 컴포넌트 공유 규칙                                         | `File_Structure.md` §3   |
| 컴포넌트 작성 규칙, PascalCase, 파일 3종 구성                                       | `File_Structure.md` §4   |
| 시각 회귀 테스트 경로                                                               | `File_Structure.md` §5   |
| 확정된 구조 결정 9건과 그 근거                                                      | `File_Structure.md` §7   |

이 절이 담고 있던 컴포넌트 작성 규칙(§6.1)은 `File_Structure.md` §4로 옮겼다. 본 백서의 §2 화면 명세, §4.3 핵심 컴포넌트 로직, §5 디자인 시스템, §7 주의사항은 변경 없이 유효하며, 그 내용을 어느 파일에 배치할지는 `File_Structure.md`가 정한다.

## 7. 개발 시 주의사항 (Implementation Notes)

### 7.1. 스타일링 전략 (Styling Strategy)

1. 토큰 → 기본 요소 → UI 컴포넌트 → 기능 컴포넌트 순으로 계층화한다.
2. 컴포넌트별 임의 여백을 줄이고 상위 레이아웃의 `gap`을 우선 사용한다.
3. 동일 상태에 다른 색상 의미를 부여하지 않는다.
4. 작성기와 리더 사이에서 같은 상태 명칭을 사용한다.
5. 콘텐츠가 비어 있을 때도 높이를 고정하지 말고 자연스럽게 축소한다.
6. 긴 한국어·영문 혼합 제목, URL, 코드, 파일명을 기본 테스트 픽스처로 사용한다.

### 7.2. 접근성 가이드 (Accessibility)

- 페이지마다 하나의 명확한 H1을 둔다.
- 단계 제목의 heading level을 순서대로 유지한다.
- 모든 입력에 영구적으로 보이는 라벨을 제공한다.
- placeholder는 라벨 대체로 사용하지 않는다.
- 아이콘만 있는 버튼은 이름과 툴팁을 제공한다.
- 오류 메시지는 필드와 프로그램적으로 연결한다.
- 모달과 드로어의 포커스 이동·복귀를 보장한다.
- 스킵 링크를 제공해 헤더·개요를 건너뛸 수 있게 한다.
- 진행률은 숫자 텍스트와 ARIA 속성을 함께 제공한다.
- 분기 옵션은 라디오 그룹, 준비물·성공 확인은 체크박스로 구현한다.
- 드래그 재정렬의 키보드 대체와 음성 안내를 제공한다.
- 200% 확대와 400% 확대의 주요 리더 흐름을 점검한다.
- `prefers-contrast`, `forced-colors`, `prefers-reduced-motion` 환경을 검토한다.

### 7.3. 예외 처리 (Exception Handling)

#### 콘텐츠가 매우 긴 경우

- 단계 본문에 접기 기능을 자동 적용하지 않는다.
- 작성기에서 긴 단계 경고와 분할 권고를 제공한다.
- 코드와 URL만 별도 overflow 처리한다.

#### 이미지가 너무 큰 경우

- 업로드 직후 예상 내보내기 크기 표시
- 최적화 전후 크기 비교
- 이미지 교체·제거·압축 옵션 제공

#### 분기 결과가 없는 경우

- 리더에서 갑자기 멈추지 않고 오류 화면을 표시
- 편집기에서는 내보내기 차단
- 현재 단계와 누락된 대상 정보를 사용자 친화적으로 설명

#### 진행 상태를 저장할 수 없는 경우

- 상단 지속 배너
- 체크 기능은 세션 동안 계속 동작
- “페이지를 닫으면 진행 상태가 사라질 수 있음” 표시

#### 다크 모드 이미지 대비 문제

- 이미지 자체를 반전하지 않는다.
- 투명 배경 도식에는 중성 체크보드 또는 흰색 이미지 표면 제공
- 작성자가 라이트·다크 미리보기를 확인할 수 있게 한다.

### 7.4. 콘텐츠 디자인 가이드

- 한 단계의 핵심 동사는 하나로 제한한다.
- 단계 제목은 가능한 한 `대상 + 행동` 형태로 쓴다.
- 명령어 앞에는 어디에 입력하는지 명시한다.
- 링크에는 `여기` 대신 목적을 나타내는 라벨을 사용한다.
- 경고는 위험과 결과, 회피 방법을 포함한다.
- 이미지에는 화면에서 찾아야 할 위치나 표시를 캡션으로 적는다.
- 오류 해결은 증상 중심으로 제목을 쓴다.
- 완료 화면에는 최종 확인 방법을 포함한다.

### 7.5. 시각 QA 체크리스트

#### 공통

- [ ] 라이트·다크 모드에서 텍스트와 경계가 충분히 구분되는가?
- [ ] 320px에서 가로 스크롤이 코드 외 영역에 생기지 않는가?
- [ ] 200% 확대에서 버튼·입력·모달이 잘리지 않는가?
- [ ] 모든 상태가 색상 외 아이콘·텍스트로도 구분되는가?
- [ ] 포커스 링이 배경과 충분히 대비되는가?

#### 작성기

- [ ] 저장 상태가 제목과 경쟁하지 않는가?
- [ ] 현재 선택한 섹션이 개요와 본문에서 동시에 식별되는가?
- [ ] 삭제·분기 변경의 영향이 실행 전에 보이는가?
- [ ] 오류 클릭 시 정확한 필드로 이동하는가?
- [ ] 모바일에서 재정렬과 블록 추가가 한 손으로 가능한가?

#### 리더

- [ ] 현재 단계와 전체 진행 상황을 항상 알 수 있는가?
- [ ] 성공 체크 전 다음 버튼이 비활성인 이유가 보이는가?
- [ ] 오류 해결을 열어도 현재 단계 문맥이 유지되는가?
- [ ] 명령어 복사 결과가 명확한가?
- [ ] 이전 분기 선택 변경 시 경로 변화가 안내되는가?

#### 인쇄

- [ ] 버튼·테마 전환·토스트가 인쇄되지 않는가?
- [ ] 단계 카드가 불필요하게 페이지를 넘기지 않는가?
- [ ] 코드와 링크가 읽을 수 있는 크기로 출력되는가?
- [ ] 경고 제목과 본문이 서로 다른 페이지로 분리되지 않는가?
- [ ] 흑백 인쇄에서도 상태 구분이 가능한가?

### 7.6. 알려진 디자인 위험

1. 작성 기능을 계속 추가하면 편집기가 노코드 빌더처럼 복잡해질 수 있다. 고급 설정은 점진적으로 노출한다.
2. 분기 구조를 그래프로 시각화하면 모바일 사용성이 급격히 나빠질 수 있다. MVP는 문장식 규칙과 경로 요약을 우선한다.
3. 카드 중첩이 많아지면 문서보다 대시보드처럼 보일 수 있다. 리더는 단계 카드 한 층을 중심으로 유지한다.
4. 경고 색상을 자주 사용하면 실제 위험의 중요도가 낮아진다. 심각도 선택 가이드를 작성기에 제공한다.
5. 독립 HTML에 웹폰트를 포함하면 용량이 커질 수 있다. 기본은 시스템 폰트로 제한한다.
6. `file://` 환경에서 복사·저장 기능이 제한될 수 있으므로 상태 메시지 디자인을 준비한다.

### 7.7. 디자인 완료 기준 (Definition of Done)

- 대시보드, 작성기, Markdown 가져오기, 미리보기, 내보내기, 리더, 완료 화면의 반응형 시안 완료
- 모든 핵심 컴포넌트의 default, hover, focus, active, disabled, error 상태 정의
- 라이트·다크·인쇄 토큰 완료
- 키보드 흐름과 포커스 순서 문서화
- 320, 390, 768, 1024, 1440px 시각 검증
- 긴 콘텐츠·이미지 없음·저장 실패·분기 오류 등 예외 상태 시안 포함
- 자동 접근성 검사에서 치명 오류 0건
- 수동 스크린 리더·키보드 테스트 통과
- 작성기 미리보기와 내보낸 HTML의 주요 컴포넌트 시각 차이 없음

- 기술적이지만 개발자 전용처럼 보이지 않음
